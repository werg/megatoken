## Native donor import follow-up

The user selected **both** DeepSeek-V4.1-Flash-1017 and Qwen3.8-Flash-Next as donors.
Importing their actual n-gram memory is required, not an optional quality experiment or
a gate awaiting comparison against cold initialization. Their ordinary token embeddings
are a separate optional baseline. See [the donor comparison](donor-comparison-2026-10-23.md)
for exact immutable revisions, table layouts, source references and licensing.

- Native extraction uses each donor's own tokenizer and reference hash addresses, retrieves
  selected rows from cloud-cached pinned source shards (or bounded HTTP ranges for small
  checks), dequantizes DeepSeek's FP8 blocks with their
  E8M0 scales, concatenates components in stable layer/order/head order, then projects and
  aggregates onto the model's longer byte-n-gram rows. Original UTF-8 context boundaries,
  source revisions, corpus identity, sampling budget, collisions and transferred bytes are
  recorded. It does not transplant donor row numbers into a different hash space. Production
  caches roughly 310 GB of selected source shards in CoreWeave after a free-disk check,
  avoiding millions of tiny HTTP requests. Only compact derived assets are collected.
- The donor maps remain independent and additive. Both regular training and DiLoCo initialize
  them before optimizer construction and restore them from checkpoints. Baking removes all
  temporary maps, preserves exact effective BF16 lookup values and keeps untouched FP32
  coordinator masters. Exported models and subsequent training phases do not need the donors.
- [The cloud preparation recipe](../configs/cloud/prepare-engram-donors.example.json) runs
  `python -m megatoken.engram_prepare` against a verified data pin, prepares both donors in a
  fixed order, and retains their license notices. Metadata downloads and sparse native table
  reads belong in CoreWeave, not on the workstation. The recipe explicitly requests 65,536
  sampled real training contexts per donor; this is a bounded extraction budget, not a claim
  that every source table row has been copied. Larger runs can reuse the source-row cache.
- Cached DiLoCo startup now sends a verified compact corpus identity to the coordinator;
  it does not try to open learner-only dataset mounts. New publication receipts/pins bind
  root, codec, chunking and feature-teacher identities. Legacy pins remain readable, but
  need metadata backfilled from verified roots before cached training launch.
- The [production-path audit](production-path-audit-2026-10-23.md) distinguishes implemented
  routes from plans and deliberate removals. Remaining actionable findings include checking
  media-output dependencies before training starts, and running final sample evaluation
  through the same memory/session route as serving. Periodic held-out training loss already
  uses the training memory path.

Independent source-address parity checks and focused extraction/training/export checks

## 8. Practical gotchas

- **`launch` refuses a dirty working tree.** It ships a snapshot of the committed tree,
  so don't edit files while a retry loop is launching.
- **A finished sandbox idles and bills until collected.** It logs
  `"bootstrap":"outputs-ready"`, and a sandbox past its lifetime is gone with its
  outputs. Watchers must wait for `outputs-ready`, then collect promptly.
- **JSON manifests are large.** Rewrite them with the detected `json.dumps` settings and
  never sort them; a reorder produces a 100k-line diff.
- **`datasets` is not installed in the dev env**, so some tests skip.
- **Hub data files must be read per file.** A repository card may declare columns that
  some files lack.
- **`ruff format --check`** flags three plan docs nobody touched; ignore them.
