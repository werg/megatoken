# Production-path audit — 2026-10-23

## Final status after the donor-path repair

This report preserves the initial production-path audit and distinguishes completed repairs from remaining findings. Detailed traces below describe the earlier code state; their old line numbers are evidence locations for that audit, not current source coordinates. The donor comparison and import workflow are documented in [the donor report](donor-comparison-2026-10-23.md). Read-only audit reproductions were followed by separate implementation tests and live cloud checks, summarized here.

### Completed repairs

- Cached coordinator initialization now receives a small verified corpus identity without dataset mounts or cache credentials. Tests exercise the actual launcher delivery and initialization with nonexistent data mounts. The existing live storage trial was backfilled and read back with all 19 original files unchanged.
- Imported donor contributions survive regular training and DiLoCo export, are folded into the served table with exact BF16 lookup parity, and seed the next phase without donor assets. Tests include updates to both learned donor maps, untouched FP32 residuals, media packs, nondefault chunking and source-asset removal. Both selected donors' actual native memories also passed a live cloud extraction check.
- Final generated-sample evaluation and the default inference benchmark now use `MultiTrackRuntime`, including session open, prompt observations, generated answers and configured collection/knowledge-base lookups. `evaluate --core-only` preserves the lower-level loss/sampling diagnostic. Tests mount a real source collection and confirm items are retrieved during metadata, prompt and generated-answer lookups.
- Media dependencies are checked before optimizer creation against actual scored media events and the active feature-reconstruction sampler. New prepared manifests carry the required output summary; legacy roots derive it from verified records. Tests cover custom stream names, generated targets, input-only media and missing generators. Both production examples now declare their required media pack path.

### Remaining production findings from the audited code state

- **Fixed effort and context defaults:** the example explicitly disables sampled effort and sets a fixed effort/history bound. This is an operational default, not a broken feature; any desired progressive context or effort schedule still needs explicit configuration and implementation.
- **Knowledge-base model identity:** bases correctly reject reuse with different weights. This is deliberate; add a clear rebuild workflow rather than relaxing the version check.

The detailed evidence below describes the audited pre-repair code state. Treat “current behavior” there as a trace of that revision; completed repairs are listed above.

## Ranked findings

### 1. Cached DiLoCo coordinator startup gap — fixed

**Confidence: high. Former consequence: a cache-backed cloud DiLoCo run failed before learner training began. Status: fixed and covered by launcher/initializer checks.**

Expected capability: the launcher's `data.cache` option restores verified prepared roots to learners and allows the coordinator to initialize the same training identity before those learners start.

Current behavior: `data_inputs()` deliberately returns no ordinary files for cached data (`src/megatoken/cloud_diloco.py:98-104`). `_restore()` fetches the cache pin and prepared roots, but `learner_job()` alone includes that step (`:163-192`). `launch()` passes the pin file and Hub/cache-key secrets only to learner sandboxes; the coordinator gets the run config URL and DiLoCo token, plus any assets explicitly listed separately (`:231-245,257-285`). The documented cache mode does not separately include prepared-root assets. The coordinator starts and runs `megatoken diloco init` before any learner starts (`:135-159,267-285`). Initialization unconditionally calls `TrainConfig.load(args.config)` and then opens `PreparedCorpus(config.datasets)` to obtain dataset and chunking identity (`src/megatoken/cli.py:111-112,164-166`). For cached configs such as `/work/data/prepared/*`, those roots do not exist in the coordinator sandbox, so wildcard expansion or corpus open fails before the coordinator can serve.

The checked-in tests encode the gap: `test_stored_data_is_restored_by_learners_before_they_train` asserts the cache has no data inputs and that the coordinator command contains no cache work (`tests/test_cloud_diloco.py:182-199`); the launch test confirms only the coordinator token/file is delivered to the coordinator and the pin plus cache secrets go to learners (`:202-239`). I ran those two focused tests; both passed, confirming the current launcher behavior (not a successful cached coordinator initialization).

**Status:** fixed by pin-bound compact corpus metadata, delivered to the coordinator and checked against selected root names, codec, chunking and feature teachers. This is not a future follow-up.

Evidence locations: `src/megatoken/cloud_diloco.py:98-104,135-159,163-192,231-285`; `src/megatoken/cli.py:111-112,164-166`; `tests/test_cloud_diloco.py:182-239`.

### 2. Media-bearing P1 runs can start without the frozen media packs they need

**Resolved in the current code:** startup checks actual scored-output modalities and active reconstruction before optimizer creation. Existing manifests are supported by a cached, checksum-verifying scan; current exports record the summary directly. A media observation used only for text prediction does not require a generator. The evidence below describes the earlier behavior.

**Confidence: high. Consequence: training fails as soon as media target or media feature reconstruction work is drawn. Not intentional for a media-bearing run.**

Expected capability: P1 trains the shared model and media conditions on its listed audio, image, video, and cross-modal streams, while the pretrained donors remain frozen. Media input features alone do not require the corresponding generator: they can be encoded as observations for text-only answers. A donor is needed when a selected loss reconstructs or generates that modality.

Current behavior: the P1 stage mixture includes media identity and generation/task streams (`src/megatoken/data/stages.json:16-20`), and the P1 DiLoCo example lists media roots and turns on the stage mixture but has no `packs:` entry (`configs/train/diloco-coreweave.example.yaml:8-20,38-39`). `TrainConfig` only requires packs for `trainable: media_bridge` (`src/megatoken/training/config.py:174-183`). Model construction omits all donors when `packs` is unset (`src/megatoken/loading.py:50-75`); selected media output targets request a resident donor for their loss (`src/megatoken/model/media.py:184-209`, `src/megatoken/model/multitrack.py:664-693`), as do requested media generations (`src/megatoken/model/multitrack.py:786-795,826-872`). Feature autoencoding requests a donor for every sampled media feature kind before checking whether that item has target latents (`src/megatoken/training/autoencode.py:141-153`). The reproduced P1 example loads successfully without packs, and a packless tiny model rejects its first image realizer request with the error above.

The stage trainer does reject missing required streams when it builds `MixtureWindowStream`, but it does not connect the selected objectives and feature sampler to pack validation. The concern applies to the checked-in P1 media-mix example: `use_stage_mixture=True` activates P1 media streams and `constraints.autoencode.items=16` activates feature autoencoding. It does not mean every media input requires a donor. If media features are used only as observations before text outputs and feature autoencoding is off, the encoder path itself does not call a donor. P1 intentionally can run text-only: `use_stage_mixture=False` plus genuinely text-only roots is accepted without packs. Preserve that route.

Recommended fix: validate the actual active paths after opening the corpus: require matching packs for selected media output targets, generated media modalities, and sampled media feature kinds in the current autoencoder (which presently requests the donor even for targetless items). For feature-only media observations with no media reconstruction/generation objective, permit a packless run. Add a packs placeholder to the checked-in P1 example because its stage mixture and autoencoder activate donor-dependent work. Fail before optimization with the missing modality named.

Evidence locations: `src/megatoken/data/stages.json:16-20`; `configs/train/diloco-coreweave.example.yaml:8-20,38-39`; `src/megatoken/training/config.py:174-183`; `src/megatoken/loading.py:50-75`; `src/megatoken/model/media.py:184-209`; `src/megatoken/training/autoencode.py:106-153`.

### 3. Final sample-quality evaluation and inference benchmarks skip transducer lookups

**Resolved in the current code:** the default `evaluate` and inference `benchmark` paths now run through the serving session runtime. `evaluate --core-only` retains the historical model-only loss and sampling diagnostic. The text session evaluator reports media and mixed observed/target meridians as skipped rather than leaking same-group targets. See [training.md](training.md) for the current commands. The remaining evidence below is a trace of the pre-repair code state.

**Confidence: high. Consequence: reported generation quality and latency do not describe served sessions. Partly intentional for synthetic/core-only diagnostics, but not labeled as a no-memory production measure.**

Expected capability: a served answer and its score reflect the memory lookups, mounted knowledge bases/collections, and adapter choices that the live session uses.

Current behavior: `megatoken evaluate` calls `training.evaluation.evaluate_records`; that function calls `model.sample` directly on a bare core state (`src/megatoken/cli.py:258-281`, `src/megatoken/training/evaluation.py:57-75`). `FacetedGenerator.sample` predicts and commits raw facets directly, without a session or retrieval engine (`src/megatoken/generation/policy.py:389-413`). The inference benchmark's non-training branch does the same (`src/megatoken/benchmark.py:231-245`). In contrast, the production session owns `TransducerInferenceEngine` and a search agenda (`src/megatoken/multitrack_runtime.py:64-81`); `open` mounts bases/collections and performs the metadata lookup (`:83-117`), and accepted observations/generation schedule lookups (`:180-263`). The reproduction showed the direct sampler has no agenda, whereas the served session lookup count advanced from 1 at open to 2 after a completed user message and 3 after terminal assistant output.

Important distinction: periodic *held-out loss* does use the ordinary training forward with `TransducerTrainer`, bank-only lookups, collection recall and mounted reading-base comparisons (`src/megatoken/training/heldout.py:1-20,95-135`). The mismatch is in the separate final generated-sample diagnostics and `benchmark` inference branch, not all evaluation.

Recommended fix: provide a final evaluation path that constructs `MultiTrackRuntime`, opens a session with declared bases/collections, and measures generation after observing the prompt. Keep direct `model.sample` for explicitly named core-only diagnostics. For latency, report both the current model-only cost and the session cost including retrieval.

Evidence locations: `src/megatoken/cli.py:258-281`; `src/megatoken/training/evaluation.py:57-75`; `src/megatoken/generation/policy.py:389-413`; `src/megatoken/benchmark.py:231-245`; `src/megatoken/multitrack_runtime.py:64-117,180-263`; `src/megatoken/training/heldout.py:1-20,95-135`.

### 4. Some stage-plan values are operationally disabled in example configs; broader context gates remain documentation-only

**Confidence: high. Consequence: a run can follow the declared token mixture and budget while using fixed effort/context settings. This is an explicit config choice and documented limit, not a broken feature.**

The executable recipe loader consumes meter, budget, stream mixture, effort mixture, `constraints.autoencode`, and `constraints.trainable` (`src/megatoken/data/recipes.py:29-46`; `src/megatoken/training/config.py:225-239`; `src/megatoken/training/engine.py:412-448`). Stage mixture use is gated by `use_stage_mixture`; effort sampling is separately gated by `use_effort_mixture` (`src/megatoken/training/engine.py:435-459`; `src/megatoken/training/meridians.py:345-349`). The checked-in P1 DiLoCo example turns the stage mixture on but explicitly sets effort mixture off and `effort: 6`; these are the example's operational defaults, so the stage's lower-effort shares do not apply unless a production run changes that flag. It also sets `max_history_tokens: 4096` (`configs/train/diloco-coreweave.example.yaml:20-39`). The intended progressive history lengths in `docs/data.md` are not schedules in `stages.json` or training code; the configured history bound applies throughout a run. `docs/data.md` explicitly labels the broader planned gates “Stage targets the runtime does not read” (`:1823-1835`), and `docs/training.md` says the history bound is configurable rather than automatically ramped (`:142-170`).

Recommended next step: when preparing a production run, decide whether to retain the example's fixed effort and fixed history bound. If the stage's effort shares or context ramps are required, enable/implement them and log the realized distribution. The current examples do not claim those settings are automatically scheduled.

### 5. Existing knowledge bases are deliberately tied to exact model weights and need rebuilding after a weight change

**Confidence: high. Consequence: an old user/corpus base cannot silently be reused after a new model export; the operator must recreate it. Known explicit limitation, not an accidental disconnect.**

The knowledge-base file records the model identity, including served weights. Mounting checks that identity and refuses a base built for a different model (`src/megatoken/transducer_service.py:55-105`; `src/megatoken/kb.py` model identity/open paths). The plan explicitly states that bases built for old weights must be rebuilt and lists reuse after small fine-tunes as unbuilt (`docs/multimodal-knowledge-plan.md:53-60,365-376`). Adding files also requires a configured preparer and pack manifest; the JSONL service creates it only when packs and a writable collection/base destination are supplied (`src/megatoken/cli.py:406-425`).

This is a safety and consistency choice. A user’s file base is also optional: served sessions can mount named bases or source collections explicitly (`src/megatoken/multitrack_runtime.py:83-117`). Recommended follow-up: provide a documented rebuild command/workflow from retained prepared features and make the model-version mismatch message point to it. No automatic refresh should be assumed today.

## Production paths checked and current status

- **Media encoder and realizers:** prepared input uses pinned teacher features; media goes through `encode_media`, shared E/C/P, and a modality-specific realizer. The donor networks are frozen outside the registered module tree; trainable conditioning weights are registered. The MB phase gate selects only the media input projection, modality embedding and realizer conditions (`configs/train/media-bridge.example.yaml:36-40`; `src/megatoken/training/engine.py:384-390`; `src/megatoken/omni/realizers.py:1-19,76-91`). Later media stages use `trainable: all` by default. Their realizer objective is reached through grouped supervised losses and the feature autoencoder. The route exists, but there is no quality or GPU-scale training result implied; the omnimodal task document explicitly says its data/quality gates remain outstanding (`docs/pretrained-omnimodal-bottleneck-plan.md:1-3,580-598`).
- **Knowledge ingestion and retrieval:** the trained transducer bank is searched by default in a session. File ingestion into a knowledge base is available through the preparer path; trained/corpus bases and source collections can be mounted, but are optional inputs, not automatically discovered. Training builds per-episode reading bases in `base_reading`, trains ingest value/key heads on matched items, and runs retrieval ranking when an episode has retrieval annotations (`src/megatoken/training/reading_base.py:29-61`; `src/megatoken/training/meridians.py:682-695`). Collection thresholds and source limits are session controls, not a fixed model behavior (`src/megatoken/multitrack_runtime.py:83-117`). The handover's threshold tuning concern is real; the threshold is adjustable and still needs empirical tuning.
- **Sparse memory learning and DiLoCo sync:** the training engine creates a `TransducerTrainer`, plans matching lookup boundaries, collects hindsight writes/write-out and gradients, then calls the sparse optimizer barrier; when using DiLoCo, the bank changes are sent through `TransducerSync` and coordinator publication (`src/megatoken/training/engine.py:365-375,734-780`; `src/megatoken/training/transducer.py:260-355`; `src/megatoken/training/transducer_sync.py`). The two-stage value behavior and bank-only switch are executable and checkpointed (`transducer.py:276-340`). Serving has no hindsight path, by design. The checked-in code path does not establish that the bank has useful learned content; the architecture docs and README call it implemented but not yet trained.
- **Owner freezing and regular served bundles:** donor weights are frozen and external to optimizer/checkpoints; learned conditions remain trainable. A served bundle stores model state and the packed transducer bank, fingerprints its required pack manifest and validates hashes (`src/megatoken/served.py:24-67,80-130`). A model-version mismatch for a separately built knowledge base is intentionally rejected. The DiLoCo-export metadata/chunking issue found elsewhere was not audited here; do not infer from this review that the full export-to-served route is gap-free.
- **Intentional removals and optional mechanisms:** v9's standalone free knowledge bank and sparse sync, literal-document source-RAG catalog/search index, semantic K/V projector, memory LoRA controllers, source/relation writers, and embedding-alignment sidecars were removed in the selected v10 architecture (`docs/continuous-state-transducer-plan.md:26,331`; the selected v10 bank is `src/megatoken/memory/transducer.py`). Current source collections live in `src/megatoken/retrieval/` and are a distinct, optional retrieval mechanism; current `megatoken kb` commands build/mount ingested transducer bases, not the removed v9 learned-KB path. Hindsight exists only in training and is not exposed to serving. The separate multi-track plan says it is a full-scope contract rather than an implementation claim (`docs/multi-track-plan.md:16-38`); the concordant media roadmap says required data/evaluation gates are not yet established (`docs/pretrained-omnimodal-bottleneck-plan.md:1-3`). Fine AV synchronization is specifically unimplemented and should not be mistaken for a current capability (`docs/multi-track-plan.md:512`).
